# 5. INTERFACE CONTRACTS & PROTOCOLS

Define clear interface contracts for every module before writing code:

1. **Port Properties:** Explicit direction, exact bitwidth, signed/unsigned qualification, and clock domain.
2. **Handshaking:** Where streaming/burst data is transferred, use standardized `valid`/`ready` handshakes with unambiguous stall and backpressure rules.
3. **Reset Behavior:** Explicit reset values for all registers and state variables.
4. **Interface Consistency:** Never change port names or widths arbitrarily. If an interface update is necessary, update all instantiated references and associated testbenches simultaneously.

---

# 6. RTL CODING STANDARDS (SYSTEMVERILOG IEEE 1800)

All RTL must be synthesizable, deterministic, lint-clean, and simulation-friendly:

* **Language Standard:** SystemVerilog (IEEE 1800).
* **Explicit Declarations:** Use `logic`, `wire`, `reg`, `signed`, and `unsigned` explicitly. Avoid implicit nets (`default_nettype none` friendly).
* **Clock & Reset:** 
  - Standardize on synchronous or asynchronous active-low/active-high reset across the design.
  - Dedicated sequential blocks (`always_ff @(posedge clk or negedge rst_n)`) for registers.
  - Dedicated combinational blocks (`always_comb`) with complete assignments to avoid unintended latches.
* **Arithmetic Precision:**
  - Explicit bitwidths for all operations, constants, and intermediate values.
  - Always guard against unintentional truncation, bit loss, or sign-extension errors in arithmetic units (MAC, multipliers, accumulators).
  - Explicitly implement saturation, rounding, and overflow detection where required.
* **Prohibited Constructs in Synthesizable RTL:**
  - No `#delay` statements.
  - No initial blocks for hardware initialization (use resets).
  - No non-synthesizable SystemVerilog system calls inside RTL.
  - No combinational loops or multi-driver conflicts.
  - No incomplete `case` or `if-else` chains in combinational logic.

---

# 7. CLOCK GATING & LOW-POWER DESIGN

When low-power or clock-enable structures are required:
1. Clearly differentiate between **functional clock enable** logic and **physical Integrated Clock Gating (ICG)** cell instantiation.
2. Use behavioral clock-gating models with latch-based glitch-free gating structures for simulation.
3. Avoid gating clock lines with raw combinational logic gates (AND/OR gates on clocks are strictly prohibited to prevent glitches).

# 8. VERIFICATION STANDARDS & TESTBENCH ARCHITECTURE

Every single synthesizable module MUST have a corresponding self-checking SystemVerilog testbench.

### 8.1 Naming & File Convention
```text
rtl/<category>/<module_name>.sv
tb/<category>/tb_<module_name>.sv
```

### 8.2 Common Verification Package (`tb/tb_pkg.sv`)
Maintain a shared verification package (`tb/tb_pkg.sv`) providing:
* Centralized test counters (`pass_count`, `fail_count`, `test_count`).
* Assertion and comparison helper tasks (`check_equal`, `check_range`, etc.).
* Standardized formatting for test headers and summary banners.

### 8.3 Standard 8-Test Verification Structure
Every testbench must implement exactly **8 distinct, self-checking test cases**:

```text
├── Corner Tests (5 Tests):
│   ├── Test 1: Active reset during mid-operation / pipeline stall
│   ├── Test 2: Boundary input values (minimum, zero, maximum range)
│   ├── Test 3: Overflow / Underflow / Saturation limits
│   ├── Test 4: Backpressure / continuous stall / empty / full conditions
│   └── Test 5: Rapid consecutive corner transitions / conflicting controls
│
├── Normal Operation Tests (2 Tests):
│   ├── Test 6: Typical sequential data stream / standard processing burst
│   └── Test 7: Multi-packet / back-to-back continuous transaction stream
│
└── Ultimate Stress Test (1 Test):
    └── Test 8: Randomized pseudorandom stimulus stress test (with fixed seed for determinism)
```

### 8.4 Self-Checking Summary Banner
Every testbench must automatically calculate and print a clear summary:

```text
================================================================
TEST SUMMARY: tb_<module_name>
================================================================
Corner Tests Passed : X / 5
Normal Tests Passed : Y / 2
Stress Tests Passed : Z / 1
Total Tests Run     : 8
Passed              : P
Failed              : F
================================================================
FINAL RESULT: [ TEST STATUS: PASS ] / [ TEST STATUS: FAIL ]
================================================================
```

A testbench must only return `PASS` if all assertions and data comparisons match the golden reference behavior. Never report `PASS` merely because the simulation reached `$finish`.

# 9. REPRODUCIBLE SIMULATION COMMANDS & SCRIPTING

Maintain a master simulation execution log at:
```text
scripts/irun_cmds.txt
```

For every newly created or updated testbench, append its exact, reproducible Cadence `irun` / `xcelium` invocation command.

### Standard Command Format:
```bash
cd work && irun -sv -access +rwc ../tb/tb_pkg.sv ../rtl/<path>/<module_name>.sv ../tb/<path>/tb_<module_name>.sv
```

* Always ensure paths in `scripts/irun_cmds.txt` are exact and match the workspace layout.
* Compile dependencies and packages (`tb_pkg.sv`, child RTL modules) in proper prerequisite order.

# 10. INTERACTIVE COLLABORATION & DEBUGGING PROTOCOL

Since Cadence EDA tools are executed in the user's environment:

1. **Step-by-Step Delivery:** Present RTL, Testbench, and the exact simulation command.
2. **Log Feedback:** The user executes the command in Cadence `irun`/`xcelium` and pastes terminal logs or error reports back.
3. **Root Cause Analysis (RCA):** If simulation fails or produces warnings:
   - Identify the exact error message and line number.
   - Explain the root cause (functional mismatch, timing mismatch, race condition, syntax error).
   - Apply the **minimal safe patch** to the RTL or testbench.
   - Update `scripts/irun_cmds.txt` if file paths changed.
   - Guide the user to re-run and verify the fix.
4. **No Fabricated Evidence:** Never claim a test passed or coverage was achieved without analyzing actual user-provided tool logs.

# 11. SYNTHESIS & TIMING READINESS (CADENCE GENUS & SDC)

Prepare front-end synthesis and timing scripts for the design so the user can validate gate-level feasibility:

1. **Synthesis Script Template (`scripts/genus.tcl`):**
   - Clean TCL script for Cadence Genus.
   - Defines target/link libraries, loads all SystemVerilog RTL in dependency order, elaborates the top-level module, applies SDC constraints, runs synthesis (`syn_generic`, `syn_map`, `syn_opt`), and outputs area, timing, power, and QoR reports.
2. **Timing Constraints (`constraints/project.sdc`):**
   - Define primary clocks (`create_clock`), clock uncertainty (`set_clock_uncertainty`), input/output delays (`set_input_delay`, `set_output_delay`), load (`set_load`), and clock transitions.
3. **Front-End Synthesis Scope:**
   - Focus is on RTL synthesizability, clock/reset tree readiness, and timing-clean front-end architecture.
   - Backend physical design (Innovus floorplanning, CTS, power routing, GDSII) is excluded from this scope.
